# Сервис назначения ревьюеров для Pull Request'ов

Микросервис для автоматического назначения ревьюеров на Pull Requests, управления командами и участниками.

## Описание

Сервис предоставляет HTTP API для:
- Создания и управления командами
- Управления пользователями и их активностью
- Создания Pull Request'ов с автоматическим назначением ревьюеров
- Переназначения ревьюверов
- Получения списка PR'ов, назначенных пользователю
- Статистики назначений

## Архитектура

Проект следует принципам Clean Architecture:
- **Domain** - доменные модели и бизнес-логика
- **Repository** - слой работы с базой данных
- **Service** - бизнес-логика и оркестрация
- **Controllers** - HTTP handlers

### Запуск через Docker Compose

1. Запустите сервис:
```bash
docker-compose up
```

Сервис будет доступен на `http://localhost:8080`

Миграции применяются автоматически при запуске контейнера.

### Локальная разработка

1. Установите зависимости:
```bash
go mod download
```

2. Запустите PostgreSQL (через Docker):
```bash
docker-compose up postgres -d
```

3. Примените миграции:
```bash
make migrate-up
```

4. Запустите приложение:
```bash
make run
```

## API Endpoints

### Teams

- `POST /team/add` - Создать команду с участниками
- `GET /team/get?team_name=<name>` - Получить команду

### Users

- `POST /users/setIsActive` - Установить флаг активности пользователя
- `GET /users/getReview?user_id=<id>` - Получить PR'ы, где пользователь назначен ревьювером
- `POST /users/bulkDeactivate` - Массовая деактивация пользователей команды

### Pull Requests

- `POST /pullRequest/create` - Создать PR и автоматически назначить ревьюверов
- `POST /pullRequest/merge` - Пометить PR как MERGED (идемпотентная операция)
- `POST /pullRequest/reassign` - Переназначить ревьювера

### Statistics

- `GET /statistics` - Получить статистику назначений

### Health Check

- `HEAD /healthcheck` - Проверка здоровья сервиса

Полная спецификация API доступна в файле `api/openapi.yml`.

## Бизнес-логика

### Назначение ревьюверов

1. При создании PR автоматически назначаются **до двух** активных ревьюверов из **команды автора**, исключая самого автора.
2. Если доступных кандидатов меньше двух, назначается доступное количество (0/1).

### Переназначение

1. Переназначение заменяет одного ревьювера на случайного **активного** участника **из команды заменяемого** ревьювера.
2. После `MERGED` менять список ревьюверов **нельзя**.
3. Пользователь с `isActive = false` не может быть назначен на ревью.

### Merge

1. Операция merge **идемпотентна** - повторный вызов не приводит к ошибке и возвращает актуальное состояние PR.
2. После merge изменение состава ревьюверов запрещено.

## Дополнительные возможности

### Статистика

Реализован эндпоинт `/statistics`, который возвращает:
- Количество назначений по каждому пользователю
- Общее количество открытых PR'ов

### Массовая деактивация

Реализован эндпоинт `POST /users/bulkDeactivate` для массовой деактивации всех пользователей команды. Это позволяет безопасно деактивировать пользователей команды, при этом открытые PR остаются с текущими ревьюверами.

## Вопросы и решения

### Вопросы, которые были решены:

1. **Порядок применения миграций**: Миграции применяются автоматически при запуске через Docker Compose. Для локальной разработки используется `make migrate-up`.

2. **Обработка отсутствующих ревьюверов**: Если в команде автора нет доступных активных ревьюверов (кроме самого автора), PR создается с пустым списком ревьюверов или с меньшим количеством (до 2).

3. **Переназначение ревьювера**: При переназначении новый ревьювер выбирается из команды старого ревьювера, исключая уже назначенных ревьюверов на этот PR.

4. **Идемпотентность merge**: Операция merge проверяет текущий статус PR и, если он уже MERGED, просто возвращает текущее состояние без ошибки.

5. **Валидация данных**: Все входящие данные валидируются через Gin binding. Ошибки валидации возвращаются с кодом 400.
